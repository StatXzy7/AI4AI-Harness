## 二、最严重的问题：gate 实现已经影响了实验含义

### 2.1 两类被允许的策略，在 gated arm 中实际上不可能通过

这是本次检查中最值得优先处理的发现。

代码中的逻辑链是：

| 位置                              | 当前行为                                                           |
| ------------------------------- | -------------------------------------------------------------- |
| `conformance.py`                | 将 `hint_guard`、`format_guard` 映射到 `plain`，注释明确说明它们允许合法的单调用提示变换 |
| `run_scenario(..., "plain")`    | 返回 `NO_MECHANISM_declared`                                     |
| `generate.py::mechanism_pass()` | 只有返回值严格等于 `PASS` 才准入                                           |
| 结果                              | 这两类策略即使通过 neutral validity，也无法被 gated arm 接纳                   |

这不是仅凭静态代码推测：`D_deepseek_s0.json` 中，`hint_guard` 的第 0、2 次尝试均为 `neutral_valid=true`，但因为 `NO_MECHANISM_declared` 被拒绝。

**为什么这是拒稿级问题？**

论文把 G 解释为“验证所声明机制是否真实执行”。但当前 G 至少还包含另一种操作：

> **系统性剔除合法的单调用提示变换类策略。**

对于每个 forced population 的八个名义槽位，其中两个——即 **25% 的槽位**——无法经这条逻辑取得 `PASS`。这不等于它们原本都会成功生成，但说明 D 与 C 的候选空间并不只是“是否验证忠实实现”的区别。

因此，D 的规模缩小及其性能变化，不能直接解释成一般意义上的“conformance verification 的效果”。**K-matching 也修复不了这一点：匹配数量不等于恢复被整个排除的策略类型。**

**必须采取的修改：**

先明确研究对象。若这是有意设计，G 应改名为“非平凡机制筛选＋机制符合性验证”，并承认它不是纯粹的 verification intervention。若并非有意，应为 prompt-level 策略定义可验证的合同，而不是简单把 `NO_MECHANISM_declared` 改成 `PASS`。

随后保留现有结果作为“原 gate 版本”的结果。修复后重新准入和评测的结果，必须作为版本化的修正实验或新验证实验呈现，**不能悄悄替换后继续声称它就是原来的预设实验。**

### 2.2 “每槽固定三次 raw attempts”与实际执行不一致

协议明确写每个槽位获得 **exactly R=3** 次生成尝试；但 `run_slot()` 在第一次准入后直接 `break`。实际实现的是：

> **最多三次尝试，成功即停止。**

对应生成日志也显示，DeepSeek 的 D/seed-0 有八个槽位，但 `raw_total=16`，而不是固定三次应有的 24 次。

这不自动意味着所有准入结果无效：在适当条件下，后续未使用尝试不影响“取第一个合格候选”的结果。但它意味着论文目前不能声称**实际消耗了严格相等的生成预算**。

建议同时报告三个量，不能混用：

**相同尝试上限、实际生成调用与 token 消耗、最终准入数量。**

未来更干净的做法是：每个 slot 一次性生成并冻结同一组三个 raw candidates，再离线应用不同准入策略。这样才能直接区分生成差异、筛选差异与成本差异。

## 三、核心科学问题：目前测到的是“稳定互补”，还是“多试几次”？

### 3.1 正确性向量不同，不足以证明 harness 的机制不同

论文目前的重要测量对象是一次执行得到的正确性矩阵 \(Y_{h,x}\)。但 R2 审计本身显示：同一个 harness 再执行，28,000 个对照单元中有 2,384 个判定翻转，即 **8.51%**。

因此，观察到两个 harness 的正确性向量不同，至少有两种解释：

**它们在不同题目上有稳定的能力优势；或者它们只是一次随机执行恰好给出了不同答案。**

当前证据没有充分分开这两种情况。

一个纯数学例子能说明问题：假设同一份 harness 代码被独立运行三次，每道题每次成功率都是 60%，不存在任何机制差异。在独立性假设下，“三次中至少一次成功”的概率为：

$$
1-(1-0.6)^3=93.6\%.
$$

大样本下，相对于一个固定运行选项约 60% 的准确率，事后 oracle 仍可呈现很大的 headroom。**代码没有变化，稳定的任务特异性能力也没有变化，但一次运行结果上的 oracle headroom 仍然很高。**

所以，当前论文需要区分：

$$
H_{\text{observed}}
\quad\text{与}\quad
H_{\text{stable}}.
$$

一种值得研究的稳定互补定义是：

$$
p_{h,x}=\Pr(\text{harness }h\text{ 在题目 }x\text{ 上答对}),
$$

$$
H_{\text{stable}}
=
\frac{1}{n}\sum_x\max_h p_{h,x}
-
\max_h\frac{1}{n}\sum_x p_{h,x}.
$$

这里所有 \(h\) 的比较集合都应统一说明是否包含 bare。这个量关注的是**跨重复执行仍存在的任务—harness 适配差异**，而不是事后从几次随机答案中挑正确答案。

这不是要求你马上把上述公式宣称为新理论贡献；它是当前论文必须明确的估计对象区别。

### 3.2 “14.5% 翻转率大于亚百分点效应，所以效应低于噪声地板”不成立

正文把三次 bare 重跑的 14.5%“至少翻转一次”比例，与 −0.16 或 −0.30 个百分点的平均效应直接比较，并据此使用“低于 noise floor”的论证。

这里比较的是不同的统计量：

| 量       | 含义               |
| ------- | ---------------- |
| 单题判定翻转率 | 执行结果的不稳定程度       |
| 平均处理效应  | 两种生成或筛选流程之间的平均差异 |
| 处理效应标准误 | 这个平均差异估计得有多精确    |

**高翻转率不自动意味着小平均效应不可估计。** 同样，平均效应接近零也不说明噪声已经被充分控制。

你可以说“执行随机性是不可忽略的变异来源”，但目前不能据此说“这些效应都落在一个无法分辨的 14.5% 测量地板之下”。

**最重要的新增对照，应是同代码 clone population：**

在相同推理预算下，比较“多个真实 harness”与“同一 harness 的多个独立重复执行”。再检查：真实种群超过 clone 对照的部分，是否跨运行、跨题目或数据库持续存在。

这比再增加几个一次性运行的 builder 更可能改变审稿结论。

## 四、统计实现与预设推断不一致，需要重算而不是只改文字

### 4.1 主分析没有实现所描述的完整重采样过程

协议和论文描述的是：

> 抽样数据库，再在抽中的数据库内抽样题目，同时保持 arm 配对。

但 `analysis_primary.py::hierarchical_paired_bootstrap()` 当前：

* 抽样了 cell；
* 对每个抽中的 cell 分别抽样数据库；
* 将抽中数据库中的全部题目拼接起来，**没有再抽样数据库内题目**；
* 不同 cell 独立抽取数据库，没有保留所有 cell 共同面对同一任务集合的完整依赖结构。

这与所宣称的方法不一致。它具体会使区间怎样变化，需要正确实现后才能知道，我不会预先断言“一定变宽”。

### 4.2 Factorial 分析实际只对 18 个 cell contrast 做 bootstrap

`analysis_factorial.py` 的区间计算是对已经算好的 18 个 contrast 重采样，没有重采样数据库或题目。脚本头部提到 Holm，但脚本本身没有生成对应的 permutation p 值与 Holm 校正结果；校正值另存于 JSON。

这里要解决的不只是“调用哪个统计函数”，而是明确推断范围：

**如果只推断这六个固定 builder 在当前题集上的表现，就不要把区间说成覆盖更广泛模型与任务总体；如果希望推广到新数据库、新生成种群和新执行，则重采样或模型必须反映这些变异来源。**

我的建议是统一推断实现：同一次 bootstrap 中，所有 arm 和相关 cell 共享一致的数据库／题目抽样；明确 builder 是固定效应还是希望推广的抽样单位；新增执行重复后，再纳入运行层面的变异。所有主结果、次结果、K-matched 和探索性结果都应调用同一套经过测试的统计基础设施。

**在这之前，−0.16 的点估计可以作为已提交产物的结果引用，但其区间不能被我当作已经独立核验成立的推断结论。**

## 六、现象归因和新颖性还需要再向前一步

### 6.1 Phase-I 到 Phase-II 的变化，尚不足以“证明 protocol sensitivity 的原因”

论文已经披露 Phase-I 的样本重叠、代理判分器、部分日志缺失等限制，也承认 Phase-II 没有重现同样的 collapse。这种透明度是优点。

但这两个阶段同时改变了多个要素：生成流程、评测样本、judge、缓存与执行实现等。**跨阶段结果不同，不能单独识别是哪一项 protocol 改变导致的。**

需要一个桥接实验：在相同 target、相同 builder、同一题集、相同 judge 和执行设置下，比较旧新生成流程。否则更合适的结论是：

> Phase-I 的观察未在修订后的 Phase-II 设置中重现，其适用范围有限；导致差异的具体因素尚未被单独识别。

### 6.2 T2 需要区分“分支没触发”和“反馈没有因果作用”

主文的 T2 使用了“执行了、反馈没有因果路径”的解释；但附录的 worked example 又说明：`react` 的首条 SQL 成功执行，所以错误修复分支没有触发。

**一次成功路径上没有发生修复，不等于修复机制没有作用。**

建议把当前分类拆得更精确：机制不存在；机制存在但本次未触发；机制触发但信息未传递；信息传递后仍未产生预期响应；实现崩溃。对于因果性判断，要依赖受控故障注入和配对测试，而不是正常执行轨迹上“输出恰好没变”。

### 6.3 新颖性应落在“可靠测量”，不能只落在“要看行为”

相关工作已经覆盖了相当接近的方向：HarnessLens 讨论行为相关验证与归因式 gate；HarnessBank 讨论语义多样性库和 gated screening；HELIX 则明确讨论可追溯 harness、候选间互补覆盖以及重复运行验证。([arXiv][2])

因此，“代码多样性不等于行为多样性”“应该看执行轨迹”“应该看候选互补”本身，很难支撑高分新颖性。

我更希望你回答一个这些相邻问题之后的明确问题：

> **当评测本身具有随机性、缓存耦合和候选准入偏差时，哪些证据足以判定生成的 harness 提供了可重复的新增能力？**

这可以形成真正有辨识度的贡献。不过，不能把修复自己项目里的统计或采集错误，直接当成已经证明的领域普遍现象。

同时，我不会把“没有全面复现这些近期预印本”当作拒稿理由。ICLR 官方指南也不允许仅因缺少同期或仅在 arXiv 上发表工作的比较而拒稿；这里的用途是帮助你明确贡献边界。([ICLR][1])

## 七、W1 是有潜力的方向，但目前不能叫“提升了 0.82 点实际能力”

对 `w1_selection.json` 的 \(k=8\) 结果拆开看：

| 指标                           | Top-accuracy | Diversity-only |             差值 |
| ---------------------------- | -----------: | -------------: | -------------: |
| Held-out oracle accuracy     |       75.95% |         76.34% | **+0.39 个百分点** |
| Held-out best-fixed accuracy |       67.48% |         67.05% | **−0.43 个百分点** |
| Headroom                     |       8.47 点 |         9.29 点 | **+0.82 个百分点** |

以上来自仓库产物，差值是算术分解。

因此，增加的 0.82 点 headroom 中，约 0.43 点来自比较基准——最佳单一成员——变弱。它并不是 0.82 点的 oracle accuracy 提升，更不是实际路由准确率提升。

此外，W1 已正确标注为 post-hoc exploratory，但代码仍存在需要统一的地方：它通过文件名通配符重新组装数据，用后写入记录覆盖先前记录，与主分析的 canonical first-write-wins 不同；其区间是对 split 平均后的 cell delta 重采样。

**我的修改要求：**

把 headroom 当作诊断指标，不要把它单独当作“种群更好”的目标。主表同时报告 absolute oracle accuracy、best-fixed accuracy、实际选择器准确率——如有——以及成本。独立验证前，把标题式结论从“diversity-aware selection transfers”降为“观察到需要进一步验证的 held-out headroom 差异”。

这里确实可能长出第二篇偏方法的论文，但不建议在当前截止前同时追求“测量论文”和“路由方法论文”两条完整主线。

## 八、达到高分接收，我建议完成哪几组决定性工作？

### 路线选择：优先做测量方法学论文

我更推荐的定位是：

**Auditing AI-Generated Harnesses: Separating Mechanism Diversity from Execution Noise**

这个标题应在对应证据补齐后使用，而不是现在只换标题。高分版本应让审稿人记住三件事：

**一种常见但被混淆的测量现象；一套能够排除关键替代解释的审计方法；一个经独立验证、可以改变实践决策的结论。**

下面按重要性排列。不是每一项都必须无限扩展，重点是让每组实验回答一个明确问题。

| 工作包               | 核心设计                                                                | 必须报告什么                                                                 | 能改变什么判断                   |
| ----------------- | ------------------------------------------------------------------- | ---------------------------------------------------------------------- | ------------------------- |
| **A：执行噪声与真实互补分离** | 真实 harness population 对比同代码 clone population；相同预算；多次 cache-off 独立运行 | within-harness 与 between-harness 差异、跨重复执行保留的优势、oracle 与实际可利用价值         | 回答“你的 diversity 是否只是多次采样” |
| **B：修正并校准 gate**  | 为所有允许的策略定义一致合同；用独立构造的正例与失败变体验证；对同一 raw pool 应用有／无 gate              | 按机制分层的误拒、误放、准入率；固定尝试上限的总效应与固定 K 敏感性                                    | 回答“你研究的是机制验证，还是选择器的结构性偏置” |
| **C：旧新流程桥接**      | 固定模型、任务、judge、缓存和时间块，只改变生成／验证流程                                     | collapse 指标、稳定互补、分支触发与错误模式                                             | 回答“跨阶段变化究竟来自什么”           |
| **D：独立实用性验证**     | 冻结选择准则，在未用于当前探索分析的新数据或新生成批次验证                                       | absolute oracle gain、best-fixed、实际选择收益与成本；与 random、top-accuracy、重复采样比较 | 回答“这套审计让使用者做出了什么更好的决策”    |

### A：重复执行必须有足够覆盖，但不要把“多跑几次”当成完整设计

可以从每个入选 harness 的 **3–5 次独立重复**开始规划，但这不是保证统计功效的魔法数字。应先根据已有重复数据做功效或精度模拟，冻结你认为有实践意义的效应大小，再决定预算。

关键是：同一题目的真实种群与 clone 对照要可比，采集时间应交错或分块，不能一个 arm 全在某天跑、另一个 arm 全在另一天跑。缓存条件也要成为明确的实验因素，而不是隐藏实现细节。

进一步，可用一组重复执行估计“哪个 harness 对这道题更有优势”，再用独立重复执行检查该优势是否仍然存在。这能检验**优势是否可重复**；但不要把这种访问过该题重复结果的分析误称为对新题的可部署路由。

### B：gate 校准要覆盖当前真正缺失的类型

当前的三个正控制、两个负变体和合同校准，是有价值的起点，但没有覆盖上述 prompt-level 准入矛盾。

高分版本需要一个独立的机制测试集：包括合法单调用改写、真正条件修复、无条件额外调用、读取但丢弃反馈、位置选择冒充投票、错误分支未触发等。校准时不能看最终 benchmark 分数。

对修正后的结果，至少区分：

$$
\Delta_{\text{policy}}
\quad\text{与}\quad
\Delta_{\text{fixed-}K}.
$$

前者回答“在同一尝试上限下采用该策略怎样”；后者回答“数量相同后，两类种群表现怎样”。两者都有价值，但不是同一个问题。

### C：不必堆很多新模型，但需要一处真正独立的边界验证

论文的“六个 builder”不等于六个独立 target 上的确认性结果。当前主确认性 target 是一个；已有探索性的第二 target 结果不能自动替代确认性迁移。

仓库中 GSM8K/MATH 方向已经有脚本、切分和 bare 运行，但本次检查到的数学 agents 目录只有 `bare.py`，audit 目录也尚不能提供完整的多-harness 比较证据。因此我不会给当前版本“跨域验证已完成”的加分。

这里有两种合理选择：完成一项结构相同的独立验证；或者诚实地保持单域论文，把单域内的因果解释与测量可靠性做到非常扎实。**一个扎实的单域结论，优于一个只有 bare 结果的“第二领域”。**

### D：允许最后得到负结果，但负结果必须排除关键解释

我不会要求新实验一定产生显著正向提升。

高分测量论文完全可以得出：

> 在排除重复采样收益、修正准入偏置并匹配资源后，没有观察到可稳定利用的额外机制互补。

前提是这个结论来自足够精确、独立、可复查的实验，而不是把一个跨零区间改写成“机制没有价值”。

## 九、项目层面的修改：从实验工作目录变成审稿人可复现产物

### 9.1 把外部执行环境纳入可追溯版本

`collect.py` 依赖 `external/TTHE` 中的 bridge、harness 基类与 agents，而 `.gitignore` 排除了整个 `external/`。这些恰好又承载缓存、加载与运行等关键行为。

这不意味着所有 harness 原始源码都不存在；仓库保存了 raw artifacts。但复现者仍需要一个明确的恢复过程：

**上游 commit＋本地修改补丁＋候选源码哈希与最终准入版本映射＋环境锁定。**

不能要求审稿人猜测作者当时本地的 `external/TTHE` 到底是什么状态。

### 9.2 所有分析必须共享一个 canonical 数据入口

当前主分析、factorial、W1 等存在不同的数据加载和覆盖方式；而完整性报告明确记录了 AD 的 3,646 次冲突、BC 的 1,191 次冲突。这里“先写还是后写”不是无关紧要的实现差别。

建议建立一个统一入口，固定并检查：

`target / harness source hash / task / repeat / cache condition / arm / membership / source file / conflict policy`。

所有表格、图、K-matched、W1、W3 都从同一个规范化数据版本生成，不能各自在 JSONL 文件里重新“捞一遍”。

### 9.3 提供三个明确的复现层级

| 层级                 | 应做到的事                                  |
| ------------------ | -------------------------------------- |
| **无需模型 API 的结果重放** | 从已归档数据重生成主表、区间、校正值、图与论文数字              |
| **无需模型 API 的仪器测试** | 跑通 stub、gate 正负控制、K=0/K=1、任务对齐、重复记录等测试 |
| **需要 API 的完整重运行**  | 说明 provider、模型标识、实际调用设置、预计调用量计算方式和凭据配置 |

最有价值的新增自动化，不是再写一个人工审计报告，而是一个**论文—产物一致性测试**：主文关键数字、图形单位、显著性标记和样本量由同一份机器可读结果驱动。

### 9.4 收口协议状态与安全事项

权威协议中仍保留“seed 2 尚未运行”等历史未完成状态，也仍把凭据撤销列为未解决事项；统计代码已经引用 D16，但该协议当前偏差列表没有对应的 D16 条目。

应保留历史记录，但另建一个与投稿 tag 对应的最终状态清单，明确什么已完成、什么是原始偏差、什么尚未解决。此次检查不能证实旧凭据是否已撤销，需单独确认；匿名补充材料也不应直接打包未经检查的完整工作目录和 Git 历史。

## 十、论文应该怎样改写，才能更接近高分版本？

### 主线收敛成三个贡献，不要同时讲五个故事

我建议主文只保留：

**测量对象的澄清：** 代码差异、轨迹差异、一次执行的正确性差异、稳定互补不是同一件事。

**可信审计方法：** 有一致定义的 gate、重复执行与 clone 对照、经过测试的统计与数据链。

**一个决定性发现：** 在独立验证中，某种被广泛使用的衡量或选择方式会误导结论，而你的审计能可靠纠正它。

Phase-I 的详细追踪案例、Arm E 的扩展合同、早期 LOHO 路由和 W3 的辅助相关性，可以主要放进附录。当前这些内容同时挤在主文里，会使中心贡献显得分散。

### 几种当前表述应统一降调

| 当前含义                                | 更可辩护的表述                                                      |
| ----------------------------------- | ------------------------------------------------------------ |
| “机制验证没有增加 routing value”            | “在当前 gate 实现与设置下，尚未发现清晰的 headroom 改善；该指标也不直接等于可部署路由收益”       |
| “collapse 已被证明是 protocol-sensitive” | “Phase-I 观察未在修订后的设置中重现；具体原因需要受控桥接实验”                         |
| “效应低于噪声地板”                          | “执行随机性不可忽略，需要在效应推断中建模或重采样”                                   |
| “超过一半效应由规模造成”                       | “K-matched 敏感性分析下的点估计缩小，但这不是已识别的因果中介分解”                      |
| “多样性选择提升 0.82 点”                    | “headroom 提升 0.82 点，同时报告 oracle 提升和 best-fixed 下降；实际收益需独立验证” |

**这些改写不能代替修复。** 它们只是保证修复过程中，论文不继续声称超过证据的内容。

### 高分版本的主图，应该直接回答决定性问题

我更希望看到三类图，而不是更多描述性柱状图：

**真实种群与 clone 种群的对照；修正 gate 前后在相同 raw pool 上的效果；固定成本下可重复、可利用收益的曲线。**

这些图能够让读者判断“代码变多究竟带来了什么”，比单独展示一次运行的 \(K_{\mathrm{eff}}/K=1\) 更有解释力。

## 十一、投稿前优先级与评分提升条件

官方当前截止为 **2026 年 9 月 18 日 23:59 AoE 摘要截止，9 月 25 日 23:59 AoE 全文截止**。投稿主文上限为九页；AI use statement 为必需项且不计入页数，补充材料也必须满足匿名要求。([ICLR][3])

建议按以下顺序推进，而不是继续并行扩散实验：

| 优先级             | 截止前应完成的工作                                                 | 对接收判断的作用      |
| --------------- | --------------------------------------------------------- | ------------- |
| **P0：立即处理**     | 明确／修正 gate 处理定义；更正尝试预算；统一数据入口；修复 bootstrap、分解表、图形单位和显著性表达 | 恢复论文的基本可评审性   |
| **P1：最有价值的新证据** | clone 与重复执行对照；修正 gate 的独立校准；最小但严谨的旧新流程桥接                  | 让中心现象具备可信解释   |
| **P1：投稿包**      | 固定 submission tag，归档外部依赖与补丁，一键重放关键结果，最终 PDF 与匿名包验收        | 让审稿人能够检查并相信结果 |
| **P2：高分增益**     | 一项完整的独立 target／领域验证，或独立数据上的实际选择收益                         | 提高结论的重要性与外推价值 |
| **P3：暂缓**       | 更多一次性 builder、更多事后相关系数、更多未闭环探索支线                          | 当前边际价值较低      |

### 什么证据会让我提高评分？

**只修文字、星号和图表：不会把我从 4 分带到高分。** 这些是基本要求。

**修复处理定义与统计链，再证明真实互补不是重复采样产物：** 我会重新考虑 **6–7 分**，具体取决于现象是否清楚、范围是否诚实、证据是否独立。

**再加上可迁移的审计方法、独立验证和明确实践价值：** 才有理由讨论 **8 分级别的强接收**。这只是我对证据门槛的判断，不是录用承诺。

**我的最终建议是：不要把主要精力放在让 −0.16 个百分点变成一个显著正数上。先证明你究竟测到了什么，再证明别人采用你的测量方法后，会少得出哪一种错误结论。**

这篇论文最有希望的高分贡献，不是“我们生成了更多不同的 harness”，也不是“我们修复了自己的评测脚本”，而是：

> **你提供了一套经过独立验证的方法，使研究者能够区分“看起来不同”“一次运行不同”和“真正新增了可重复能力”。**
