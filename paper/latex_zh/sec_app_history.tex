\subsection{早期生成协议探查及其局限}\label{sec:phase1probes}
Phase I 还探查了生成侧修复——策略强制自由形式协议（指派机制，导入／冒烟准入）与编译式 Harness IR。在策略强制协议下，三个构建器中有两个产生的程序群体点估计超过预先指定阈值（Qwen3.8-Flash 5.96、DeepSeek-V4-Flash-Vision-Exp 7.95\,pp；旧协议臂为 4.64\,pp 未达标），且逐策略接纳随构建器身份排序（在有日志工具下 GLM-5.3-Flash 3/8、Qwen3.8-Flash 7/8、DeepSeek-V4-Flash-Vision-Exp 8/8）。这些观察为 Phase II 提供动机，但不是验证性的，原因有三并已披露：设计是两个嵌套对比，无法把协议主效应与构建器主效应分开；早期运行缺少逐尝试日志，预算相等无法审核；准入是导入／冒烟检查，不是 \S\ref{sec:f2-admission} 的反事实一致性门控。完整条件见附录~\ref{app:phase1-provenance}。

\paragraph{生成空结果失败（M0）。}用 Qwen3.8-Flash 与 DeepSeek-V4-Flash-Vision-Exp 构建器重跑原优化循环，产生 40 个与 \bare{} 基线源码逐字节相同的候选。代码同一并不意味着随机执行也相同。这次运行没有提供不同代码的程序群体；它作为另一种更原始的失败模式报告——流水线根本没有产生不同程序群体。上述坍缩主张完全基于来源确实不同的发现阶段程序群体。

\paragraph{图数据。}图~\ref{fig:phenomenon} 比较所测 harness 对的源码相似度与正确性分歧。

\paragraph{固定的历史记录局限。}早期自由形式程序群体在会话中产出，其生成工具与逐尝试日志未被保留，因此无法从这些历史记录中恢复预算相等的验证。其准入是评估时的导入／冒烟检查。后续带日志的生成过程使用最多三次尝试、16{,}384 token 预算，并记录每次尝试的阶段和结束原因。完整的逐策略网格与构建器接纳排序（3/8、7/8、8/8）来自该带日志过程，分析发生在准入决定冻结之后。

\subsection{上游代码提取审计}\label{app:extraction}
在 36 个强制 C/D 单元中，全部 108 次 \texttt{format\_guard} 尝试均未通过中性有效性：71 条日志报告 Python 字符串未终止，36 条报告无 Python 围栏，1 条报告提供方超时。存档生成器的非贪婪 Python 围栏提取器在随后第一个三反引号处终止，包括 Python 字符串内部的三反引号。三个合成的、语法有效、在普通字符串、文档字符串或正则中包含 SQL 围栏的程序变成了无效前缀；而提取器仍把其截断标志设为 false。审核的提取器与保留实现一致，但历史尝试记录无法验证当时实际执行的版本。完整构建器消息未被该生成器保存，这是固定的历史记录局限。合成示例确立了提取器的截断行为，历史失败模式则与相同机制相容。我们找到 74 个保留的提取程序，全部语法无效；其中三个与无围栏日志并存，作为来源冲突保留，不归属于那些尝试。这些发现把一个生成接口失败置于门控显式策略排除之旁。



\subsection{历史 BIRD 选择分析}\label{app:rich}
选择分析与附录~\ref{app:bird-fingerprints} 的指纹分析都是对存档验证性单元（18 个构建器$\times$种子单元、384 个接纳候选、core-400 结果）的事后分析。两者使用与主重分析相同的记录合并规则、固定任务与成员身份检查。它们描述此前已分析任务上的选择表现。

\paragraph{多样性感知选择。}每个单元合并跨臂的全部接纳候选。重分析保留旧种子、100 次随机数据库对半划分、每划分每单元 200 次随机子集抽取及候选选择规则。它记录一个新的确定性调度：历史的集合派生单元顺序未存档，因此仅凭种子无法恢复相同的历史划分与抽取。选择使用开发数据库；评估使用互补数据库。$1{,}800$ 个单元—划分估计在划分间共享任务。方法为开发准确率 top-$k$、均匀随机子集、贪心开发 oracle 覆盖、以及贪心平均准确率加 $\lambda$ 倍 oracle 覆盖（$\lambda\in\{0.25,0.5,1,2\}$）。所有候选选择都在划分的评估之前于划分内冻结。

表~\ref{tab:selection} 在每个被评估子集中保留共同的 AD single-call；$k$ 只计候选。仅候选估计与包含基线的估计分开记录，以区分历史估计目标。Oracle 与最佳固定使用留出结果作为描述性上界。开发固定改为用开发准确率选一个成员，成员名并列时升序、single-call 优先。确定性方法本就保留一个全局开发最佳候选；该比较器的差异可能来自哪些并列最大值存活，而非开发最大准确率提高。

\paragraph{为何弃用历史重选择区间。}
历史数据库划分比较曾考虑正权重重选择百分位区间，当前不确定性估计不使用该区间。以下精确反例解释弃用原因：这一构造不存在普遍的 95\% 覆盖保证。令九个独立数据库各含一个 Bernoulli($p$) 任务状态。16 个固定候选由八个状态 0 专家后接八个状态 1 专家组成；single-call 恒错。把 canonical $k=8$ 规则应用于四个开发库与五个留出库。在记录的并列规则下，仅多样性减 top-acc 提升空间统计量的期望为 $(1-p^4)\,\mathbb{E}[\min(B,5-B)/5]>0$，其中 $B\sim\mathrm{Binomial}(5,p)$。在全部九个状态恰好相同的事件上，每种正加权都给两种方法产生零提升空间，故百分位区间为 $[0,0]$。因此覆盖率至多为 $1-p^9-(1-p)^9$，在 $p=0.1$ 时为 61.26\%。对相同单元或重叠固定划分取平均不能移除该事件。该失败针对这一特定区间构造。

\subsection{路由与探索性选择}\label{sec:boundary}
Phase-I 留一 harness 预测器在所测 DeepSeek 程序群体中相对最佳固定 harness 的变化为 $-3.4$\,pp；Qwen 的估计为 $+0.9$\,pp（95\% CI $[-5.2,+6.9]$\,pp），题目留出的修复 AUROC 为 $0.512$。这些结果显示所测程序群体的预测区分能力很弱。表~\ref{tab:selection} 研究另一问题：子集构造如何改变留出 oracle 覆盖率、固定成员准确率及提升空间。

\subsection{档案诊断与共同集 MATH 重评分}\label{app:archive-analysis}
BIRD 档案诊断涉及 18 个 Phase-II 单元。在 BIRD 上，完整性类（A）对每个单元为 REFUTED\_WITHIN\_SCOPE：冻结输入清单包含重叠的采集记录，其行在 canonical 键上重复（由存档的先写先得策略解决，并记录判定冲突计数），因此下述覆盖数字在该去重视图上计算。全部单元显示单次覆盖（B SUPPORTED）；稳定性、可选择性与可部署性为 INSUFFICIENT\_EVIDENCE，这些诊断使用单次运行档案记录。逐记录逻辑调用在与其余重分析相同的规范化去重视图上读取（$\RevisionCostRows$ 条候选–题核心子集记录上共 $\RevisionLogicalCalls$ 次调用，表~\ref{tab:cost}），成本汇总据此采用已记录的逻辑调用数。
MATH 当前审核使用与正文相同的 $36\times\RcvPairedN$ 完整单次评分矩阵。冻结评分器重放复现全部 $\RcvSingleCells$ 个评分；版本化端点敏感评分器在该子集上产生相同评分。版本化产物保留早期档案审核发现。正文结果始终使用原始评分。旧档案选择政策与重评分输出保存在历史产物中；当前政策结果使用不变的开发集训练选择器与共同完整题集（附录~\ref{app:selection}）。

\subsection{隔离的 MATH 提示协议试运行}
较早的试运行错误地提供了 GSM8K 风格描述，其数值答案格式与 MATH-500 不符。代码检查发现一个先生成再验证的 harness，验证器几乎拒绝所有答案，回退返回过时循环变量或零。这些定性失败说明提示接口问题；试运行的性能结果采用不同范围，不进入当前 MATH 表格。
