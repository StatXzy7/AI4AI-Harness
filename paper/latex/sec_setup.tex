\subsection{Harnesses and harness
value}\label{harnesses-and-harness-value}
Following the harness-abstraction of TTHE, a \textbf{harness} \(H\) is a
program that wraps a frozen target model \(M\): it receives the
natural-language task input \(x\), issues one or more calls to \(M\),
optionally executes intermediate artifacts (e.g., SQL against the
database), and returns a final answer. Execution accuracy is scored
programmatically. For a task \(x\), we define the \textbf{harness
marginal value}
\[\Delta(x, H, M) \;=\; Y(x, H, M) - Y(x, H_0, M) \in \{-1, 0, +1\},\]
where \(H_0\) is the bare single-call baseline and \(Y \in \{0,1\}\) is
programmatic correctness; \(+1\) is a \emph{repair} (raw wrong, harness
correct), \(-1\) is \emph{harness-induced harm}. The deployment question
that motivates this paper --- predict \(\Delta\) before executing \(H\)
--- presupposes that \(\Delta\) is not almost-always zero. A population
of harnesses in which every harness reproduces the raw model's outcomes
offers nothing to predict or route over. Our first contribution is to
take this presupposition seriously and measure it.
\subsection{Domain, target, and data
splits}\label{domain-target-and-data-splits}
We instantiate the problem on \textbf{BIRD text-to-SQL} (SQLite), whose
answers are judged by execution against gold query results --- no
model-based grading. The target model is frozen throughout:
\textbf{GLM-5.3-Flash} served through an OpenAI-compatible endpoint
(temperature 0); builders differ only in how harness \emph{code} is
produced. The \textbf{builder-visible set} \(D_{\mathrm{build}}\)
contains 8 \texttt{card\_games} questions; the \textbf{evaluation set}
\(D_{\mathrm{eval}}\) contains \textbf{151 questions} (121
\texttt{card\_games}, 30 \texttt{formula\_1}), held out from all
builders. We disclose two overlaps explicitly: (i) 24 of the 151 items
were also used in day-1 protocol-development measurements (their day-1
outcomes informed the diagnosis of Section~4, not any generation input);
(ii) the four human control harnesses (Section~5) were designed after
inspecting day-1 traces on these tasks, so the control's headroom is an
existence proof rather than a blind estimate. Populations are generated,
frozen, and hashed \emph{before} any evaluation on
\(D_{\mathrm{eval}}\).
\subsection{Populations under
comparison}\label{populations-under-comparison}
We compare seed baselines (\texttt{bare}; \texttt{react}, shipped with
TTHE), four AI-generated populations (each \(K=6\): condition A, the old
proposer protocol; conditions B/C/D, strategy-forced free-form with GLM /
Qwen / DeepSeek builders), a compiled IR arm, and the human positive
control (four hand-written harnesses with forcibly distinct execution
paths). The old-protocol population A is selected for behavioral
diversity using \emph{only} the 36 earlier-run questions disjoint from
\(D_{\mathrm{eval}}\), by a selection rule frozen before the 151-item
evaluation; condition B is the audited logged re-run (B3, K=3), the
original unaudited 09-01 run being disclosed as a provenance caveat
(Section~6, Appendix~B). Every harness is accepted only after passing a
smoke check (it runs and emits executable SQL); the free-form arm
additionally passes the execution-path gate of Section~6. Full condition
definitions appear in Appendix~B.
\subsection{Design structure and pre-specified decision
criteria}\label{design-structure-and-pre-specified-decision-criteria}
\textbf{The design is two nested contrasts, not a full factorial}: the
protocol contrast at a fixed builder exists only for GLM (A vs B), the
builder contrast exists only under the gated protocol (B vs C vs D), and
the IR arm has a protocol axis but no builder axis. Section~6.2
completes the old-protocol row for the Qwen and DeepSeek builders; we
interpret each contrast within its own fixed factor and do not claim to
separate main effects. Before running any 151-item evaluation, admission
thresholds were frozen in the project decision log (union repair over
bare errors $\geq$ 15\%, oracle headroom $\geq$ 5 pp, $\geq$ 3 harnesses with
pairwise-distinct non-empty repair sets), with the v6/v7 audit trail
documented in Appendix~C; admission is decided on point estimates by the
frozen rule, and Section~6 marks populations whose bootstrap intervals
include sub-threshold values.
